# Isolated Explore search load testing

The native harness executes the real `search_public_explore_session` migration and its private queue tables. It uses the standalone fixture at `tests/fixtures/explore-search-session-bootstrap.sql`, then inserts synthetic public Explore documents. It does not load or stress production, and refuses remote database URLs and database names other than `explore_load` or `explore_load_<suffix>`.

The initial Windows runtime came from the Windows x64 PostgreSQL 17.11 binary ZIP linked on the [official EDB binaries page](https://www.enterprisedb.com/download-postgresql-binaries?lang=en), also referenced by the [PostgreSQL Windows download page](https://www.postgresql.org/download/windows/). The ZIP was saved as `work/explore-load-runtime/postgresql-17-binaries.zip`. Only `pgsql/bin`, `pgsql/lib` and `pgsql/share` were extracted. This is a local process bound to 127.0.0.1, not a system service. Docker Desktop could not start its inference manager; it was not reset.

Start the isolated server:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-explore-benchmark-postgres.ps1
npm install --prefix work/explore-load-runtime --no-audit --no-fund pg
$env:EXPLORE_BENCHMARK_DATABASE_URL='postgresql://explore_bench@127.0.0.1:55439/explore_load'
node scripts/benchmark-explore-search.mjs --schema=tests/fixtures/explore-search-session-bootstrap.sql --corrections=supabase/migrations/20261009062031_explore_booking_rank_gate.sql,supabase/migrations/20261009064031_explore_region_index_predicates.sql,supabase/migrations/20261009065531_explore_session_publication_cutoff.sql,supabase/migrations/20261009071031_explore_candidate_seek_paths.sql --scales=100000,500000,1000000 --concurrency=1,8,16 --samples=180 --workload=extended --events=true --output=work/explore-load-results/search-native-scale.json
```

The runtime uses a dedicated role and database, 256 MB shared buffers, 8 MB work memory, JIT off, and `pg_stat_statements.track=all`. Every measured search call has a three-second statement timeout. The harness records the base migration SHA and every applied correction SHA, and refuses a different base on later runs. For a changed base migration, create a fresh dedicated `explore_load_<suffix>` database. It never drops an existing database. Synthetic seeding temporarily removes non-primary-key projection indexes, bulk inserts, then recreates the exact saved index definitions; measured queries always run after all indexes are restored and tables analyzed. `--seed-mode=incremental` keeps indexes during insertion when import cost itself is the subject of testing.

The basic workload searches `Nail place`, `King Nails` with an expandable city scope, broad `nail`, Nails/WI, nail/Milwaukee, GPS near Milwaukee, and guest browsing. `--workload=extended` adds nearest/relevance GPS, newest, canonical bookable ranking, short prefix, national/GPS empty results, sparse non-exact GPS words and fuzzy fallback (18 cases). It loads up to three pages with the returned cursor and checks duplicate salon IDs inside the session. `--workload=deep --pages=50` crosses multiple 256-candidate pools for state and GPS continuations.

Synthetic data includes skewed state distributions, dense GPS regions, missing coordinates, exact duplicate names, service categories, varying profile completeness and booking settings. Deliberately correlated category/quality fields exposed an index plan that rejected over 100,000 unrelated rows to return 256 matches. Default coordinates are known for approximately 92.3% of rows; `--coordinate-ratio=0.05` creates a separate sparse fixture rather than claiming the dense distribution matches production. `--reuse=true` preserves an existing matching-size dataset but rejects a coordinate-distribution change. These are anonymous search workloads; they do not represent personalized feed traffic or a million social posts.

Reports contain p50/p95 per group and per case, separate first-page and continuation timings, request throughput, errors/timeouts, duplicate IDs, explicit SQL RPC count, nested statement counts/returned rows/block activity, and candidate `EXPLAIN (ANALYZE, BUFFERS)` plans. Continuations from an already-ranked queue are much cheaper than first-page candidate selection, so their aggregate percentile must not be used to describe first-page cost. `pg_stat_statements.rows` measures returned rows, not every row inspected. `planNodeRowVisits` counts visits and filter rejections across nodes in representative candidate plans and can count a row multiple times; it is not a distinct global scanned-row count.

`scripts/profile-explore-candidates.mjs` compares exact raw candidate paths and continuation anchors. `scripts/profile-explore-geo-probes.mjs` compares capped geographic hit probes and existence guards. A limit of 256 returned candidates does not guarantee only 256 index entries were examined: a dense geographic bitmap may contain more than 100,000 points, and filtering may reject many entries before a KNN pool is full. These plans establish practical work for the tested distribution, not a universal constant-cost claim.

Measurement limits:

- These are native PostgreSQL concurrent connections on the local workstation. PGlite correctness tests do not substitute for this concurrency measurement.
- SQL times do not include Internet latency, server rendering, reputation/profile enrichment, media delivery or actual Safari behavior.
- Setup/analyze and earlier samples can warm buffers. There is no operating-system cache eviction, so reports must not be described as fully cold disk measurements.
- Concurrency refers to simultaneous SQL session workers, not a proven number of online users.
- Other workstation processes and database writes can affect measurements. Production resources and traffic can differ substantially.
- A successful million-document search benchmark does not establish the capacity of all Social Discovery branches. Those need their own feed/post/interaction fixtures and workloads.

Stop the dedicated server after testing:

```powershell
& 'work/explore-load-runtime/pgsql/bin/pg_ctl.exe' -D 'work/explore-load-runtime/data' -m fast stop
```

The database files and JSON reports remain for review. No universal p95 or production load guarantee is inferred from these results.

## Public video support boundary

The current organic public upload and Explore rendering paths support photos, not native video. `lib/salon-profile-media.ts` and `lib/beauty-media.ts` admit only JPEG, PNG and WebP, generate `.webp` paths, and validate those paths. Salon and beauty composers process uploaded images through a browser canvas and emit WebP. Server validators recheck the stored image MIME; storage bucket migrations allow only these image types, and the beauty media schema also enforces image-only MIME values and image/before/after roles. `app/explore/explore-feed.tsx` renders media with `next/image` and an `imageUrl`. The admin safety-review player can preview a video URL, but that is not a public upload or Explore playback feature.

Native video therefore needs its own upload/processing feature: trusted MIME/path/schema handling, limits and codec/duration validation, posters, processing states, compatible output or managed transcoding, public player behavior, and delivery/Safari tests. The existing candidate/session architecture can carry future video metadata after those changes, but the current million-post measurements use image-based sources and do not prove video uploading, transcoding or playback capacity.

`social-native-1m-zero-final.json` separately tests the anonymous feed with all source and projection coordinates removed. Strict GPS pages return no items; expandable GPS Discovery/Latest pages contain only `wider` items. Manual city/state pages still use their chosen area. This establishes fallback labels without claiming nearby distances from missing data.
