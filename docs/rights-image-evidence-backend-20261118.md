# Private image evidence and pinned public-origin removal

Implementation candidate on baseline `a4fe43e2da823586f52b1a5a4f309d0769b3d14d`. This is source work and isolated synthetic acceptance, not production activation, a storage cleanup run, a copyright determination or a complete rights-operations claim. No real image was downloaded, copied, deleted or sent to AI. No provider credentials, environment files, role grants, deployment or Apple writes were used.

## Policy and actual operator authority

The owner approved ordinary photo evidence deletion **30 days after the case is explicitly `closed`**. `resolved`, a content decision or capture time does not start that period. Reopening returns an ordinary case to no closed-case deadline; reopening never recreates purged bytes. The owner identified the Support team and `support@reylumi.com` as operational; this is owner-attested, not an independent delivery test.

The migration seeds policy version `ordinary-photo-closed-30d-20261118` **disabled**. No membership, assignment, enabled flag, retention exception or legal hold is activated. Assignment uses the existing report's `assigned_membership_id`, active membership/user and `admin.reports.read/update`; salon membership, reporter identity, customer access and generic Support attachments grant no evidence access. The canonical post-safety case resolves its existing linked Support report, with its original platform report as fallback. An unassigned case fails closed.

A separately approved legal hold requires its reason, owner authority receipt and review date. Hold editing is privileged configuration, with no ordinary operator API or new role grant. An overdue review blocks ordinary evidence access/work; its review date is not automatic hold release. An ordinary hold does **not** override personal account erasure. V1 rejects `retain_on_account_erasure=true`; retaining evidence beyond erasure needs a separately reviewed implementation/exception. Unknown, suspected or known CSAM/minor-safety cases take a separate escalation lane; the routine worker does not download, escrow, classify or restore that material. Matching object/case and known exact-byte SHA-256 risks apply across cases, preventing an ordinary complaint from bypassing another case's risk flag. A later special-risk flag also blocks routine expiry purge; an existing byte copy then needs the separate lawful handling decision, and erasure cannot falsely complete while its required object remains.

## Deliberately bounded supported source

Only new, fully pinned `public_post_images.status='approved'` objects in `beauty-profile-media` or `salon-profile-media` qualify: WebP, 1–512000 bytes, immutable approved object ID/version/eTag/SHA-256/size/MIME matching Storage. These are the exact final published bytes, not necessarily the camera original. Legacy/incomplete registrations, arbitrary URLs, caller-selected buckets/paths, avatars, identity covers and unreviewed business files are excluded.

The private `rights-review-evidence` bucket is nonpublic, WebP-only and bounded to 512000 bytes. DB-generated keys are `v1/<case UUID>/<evidence UUID>.webp`. There is no upsert, private-key resurrection, direct anon/auth read/list/sign/write or reusable signed evidence URL. Restrictive policies defeat older broad Storage policies. Exact final bytes are hashed on source download, private readback and again on the separate origin-removal pass. SQL metadata checks complement those full-byte checks; eTag alone is not a cryptographic receipt.

## Separate state transitions and API contract

1. `request_rights_image_evidence(case, opaque manifest object ID, request UUID, triage, reason, false)` authenticates the assigned operator, binds the exact canonical case/media and records immutable request identity. Initial removal intent is rejected. No supplied URL is fetched. Policy disabled or unknown risk produces a blocked/escalation receipt with no byte operation.
2. `claim_rights_image_evidence('capture')` leases bounded service work. Worker revalidates authority before each Storage operation, downloads/hashes, uploads with `upsert:false`, downloads/hashes the reserved private object and calls `finish_rights_image_evidence_capture`. SQL pins the actual private ID/version/eTag and requires the original source identity still match. Uncertain upload/checkpoint responses reuse the same object identity; an unverified copy never authorizes deletion.
3. `get_admin_rights_image_evidence_state` returns a current opaque version, capture/removal status, ordinary retention/hold summary and an explicit removal-block reason. `request_rights_origin_removal(evidence, request UUID, expected version, reason)` is a **separate** assigned-operator decision with an immutable receipt. Same-UUID replay precedes current-version validation; changed payload reuse conflicts. Closing/resolving Support does not request removal.
4. `claim_rights_image_evidence('remove_origin')` requires that decision, a verified private copy and no public references. The original source post must already be terminally deleted; an active, hidden, archived or appeal-held post is still a reference. Covers, logos, staff portraits, booking history, other posts, saved/published Market selections and ad-report evidence block removal. Other cases need their own valid private receipt. No business record, shared cover/history or financial fact is detached automatically.
5. The permanent old-source-key fence is installed under shared manifest authority before returning removal work. The worker verifies private bytes again, revalidates and invokes exact Storage API removal. The Storage transaction independently checks the active stage/lease, exact original tuple and current references. SQL finishes only after actual source absence. Case metadata/status updates can retain their unchanged historical source snapshot through evidence-only linkage; they cannot reattach or restore the fenced public key.
6. `claim_rights_image_evidence('purge')` is separate ordinary closed-case expiry work. It pins an existing reserved private object even after a lost capture checkpoint, and only confirms purge after Storage absence. Hold/reopen and final Storage deletion serialize through the report lock. A pending purge lease blocks an immediate reopen until it completes/expires; adding a properly approved hold cancels an unspent purge lease. The coordinator separately wires the existing authenticated maintenance cadence; this SQL does not configure a cron service, enable the evidence policy or create an operator UI.

Worker/access implementation is owned by the parallel runtime patch: `lib/rights-evidence-{storage,worker,access}.ts` and the protected evidence GET route. The route authorizes the current operator twice, verifies all bytes before releasing any range, returns `no-store`/`nosniff` headers and never returns Storage pointers. Source actor IDs, internal pins and private keys are server-only RPC data. Its current source hashes are bound in the isolated acceptance receipt.

## Lock, failure and erasure boundaries

The service lock order is user → shared exact-byte risk fence → manifest → evidence job → report, with `NOWAIT`/nonblocking advisory locks rather than reverse waits against prelocked post/asset/Storage/report writers. New special-risk requests and minor-safety case changes take the exclusive hash fence, serializing their accepted DB transition with private capture/purge commits. This is not a persistent global illegal-image registry. An already-started network download cannot be recalled; a later flag blocks the private commit and further ordinary work, and no AI transfer exists here. Removal upgrades the manifest lock before installing its permanent fence; checkpoints acquire matching media assets with `NOWAIT`. Reference helpers are `VOLATILE` so post-lock reads and same-RPC return values use fresh snapshots. No transaction is held open across Storage requests. Service claims are capped at three with five-minute leases; the runtime uses a stricter single-job and bounded-request budget.

The shipped exact-existing-byte, leased `retain_business` same-path COPY authority stays intact; the original guard still validates its lease/metadata. New private evidence is service-owned, so account erasure explicitly plans **all reserved private paths**, including late/uncheckpointed uploads, before manifest tombstoning. A pending/complete erasure job denies late capture. Ordinary evidence and ordinary holds are erased with the account. Strict erasure object and final Auth checkpoints remain authoritative; no direct `storage.objects` deletion is used.

Transient Storage failures remain retryable. Wrong source/private identity is a conflict requiring reviewed resolution, not permission to delete a replacement. A permanently mismatched private object is not automatically swept. Removing an origin does not prove CDN invalidation, previous-link failure at every edge, browser/download recall or third-party deletion; those remain separate runtime checks. No public restore of the old key exists.

## Legacy and broader rights requests still require a reviewed lane

Production's existing unpinned photos are **not covered** by this new-only pipeline. Support can accept and triage a complaint, but that does not make origin removal for every existing image operational. Before authorizing any real operation, prepare this exact per-case package:

- Triage special illegal/minor-safety material first; use the separately approved escalation process, without routine evidence copy or AI transfer.
- Resolve the reported display to canonical object/use IDs. Enumerate the source post, separate Beauty cover copy, salon/avatar/logo/staff use, Market selections, booking/business history and any **known** identical copies. A claimant URL is not an arbitrary server-fetch permission or proof of ownership.
- For each approved ordinary legacy target, obtain its exact current ID/version/eTag/MIME/size and bounded full-byte SHA-256 through an authorized operator lane. Missing bytes or incomplete metadata must be recorded as unavailable. A future legacy registration must atomically fence relevant writers, pin that exact identity and recheck it; a metadata preflight followed by an unguarded delete is insufficient.
- Approve each shared use's disposition separately: retain under lawful private business access, replace the public display, migrate to a new reviewed key or remove the exact use. Do not erase POS/payroll/Tax histories or a bucket/user prefix to satisfy a photo complaint.
- Preserve verified private evidence only under the approved ordinary policy, then exact-object Storage API removal and absence checkpoint. Retention beyond personal erasure, exceptional evidence-unavailable removal and restoration require their own approved authority and implementation.
- Verify origin, known duplicate uses, transformed/previous links and edge behavior independently. A known-identical NCII copy workflow or statutory deadline cannot be claimed complete from this limited manifest helper or a copyright report reason. Global discovery/removal, identity-image rights tools, private business-history migration and specialized escalation remain explicit gaps.

The actionable next step for those excluded objects is a reviewed canonical pin/per-use disposition extension and an authorized synthetic/hosted rehearsal; it is not a blanket manual-delete recommendation. Real data operations, enabling the policy and assigning actual operators remain outside this source-only work.
