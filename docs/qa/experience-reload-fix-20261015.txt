Cause and history
The preceding progressive-cache implementation added an authorization gate for
retained React Activity pages. Its fetch monitor treated every POST and Server
Action as a mutation. Read actions invoked by ExploreSalonLove and the delayed
OwnerCampaignRuntime therefore hid the Activity, stopped its effects, then
restarted those same reads after validation. Telemetry POST requests could also
invalidate the entire cache. The original source reproduced 14 effect cleanup
cycles in 3.2 seconds, and three delayed campaign cycles in 7.2 seconds.
These cycles often looked like a document reload even with an unchanged session.
Real reload paths for identity, permission and resource-access changes also
lacked a persistent bound across documents.

Correction
- Read actions and passive search/delivery/telemetry POSTs do not invalidate
  retained page state. Actual Server Action changes use Next 16.2's revalidation
  response signal; explicit server data/scope hints remain supported.
- Data writes refresh resources in the active account scope and recheck current
  grants without hiding an already authorized page. Settings and service-relay
  writes explicitly revalidate their affected retained views after success.
- A pre-save context response cannot authorize post-save state. Responses from
  disposed/old session fetch wrappers cannot invalidate a new session. Nested
  admin and ordinary providers both recheck their own grant fingerprints.
- Foreground, account, permission and access-rejection gates remain fail closed.
  Network failures retain bounded retries and a usable retry action.
- Automatic document recovery is limited across documents using session storage.
  Repeated or unpersistable recovery keeps protected content hidden and offers
  an explicit Reload button. The limiter stores only time and reason.
