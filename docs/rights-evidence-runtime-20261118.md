# Private rights-image evidence runtime

Source baseline: `a4fe43e2da823586f52b1a5a4f309d0769b3d14d`. This is a local implementation candidate. It does not activate policy, assign an operator, submit an Apple declaration, or claim production removal. The separate SQL change owns policy, operator authority, risk triage, immutable identities, leases, shared-reference checks, account-erasure integration and retention transitions.

## Supported scope

Only fully pinned **approved** Beauty/Salon post stills are accepted: exact normalized `image/webp` bytes, at most 512,000 bytes, canonical post-image paths, Storage object ID/version/eTag, SHA-256 and size. No normalization, AI or remote-URL fetching occurs in this workflow. Legacy/unpinned objects, avatar/cover uploads and financial/private-workflow buckets are excluded. A shared cover, booking/history/Market selection, other live post or another case without its own valid private receipt remains a blocker under the SQL authority. This is not an unrestricted rights-removal service for every existing image.

The dedicated private bucket is `rights-review-evidence`; the immutable reserved path is `v1/<case_id>/<evidence_id>.webp`. Internal evidence never becomes a reporter-visible Support attachment or a reusable signed URL. The current source policy starts disabled, and no new assignment or role grant is made by these files. A report or evidence request is not removal approval.

The owner selected ordinary evidence retention for 30 days **after explicit case closure**, rather than after resolution or capture. SQL computes that deadline. A null `retain_until` can represent an open/reopened case or a separately approved ordinary hold; the worker never invents a date or hold. Purge requires a finite expired deadline and fresh SQL authority. This v1 forbids a hold from overriding personal account erasure; all reserved private paths participate in that erasure. Unknown/suspected/known CSAM or `minor_safety`, including another case involving the same exact bytes, is outside ordinary capture/read/removal/purge: it needs the separate escalation path, without routine source download, escrow or AI. No special-risk handling workflow is implemented here.

## Worker and recovery

`lib/rights-evidence-worker.ts` exports `processRightsImageEvidence(client, row, stage, deadline)` and `runRightsImageEvidence(stage, client?)`. Each bounded pass claims at most one job for one explicit stage; it does not capture and remove in one loop. The pass has a 45-second new-work budget and requires a 12-second lease/request margin. SQL uses the five-minute lease and revalidates current policy/operator/risk, exact objects and references. Every Storage operation follows affirmative revalidation; SQL Storage guards remain the race boundary after that request.

| Stage | Required work before reporting success |
| --- | --- |
| `capture` | Read the pinned source, verify the complete size/MIME/SHA, upload the exact bytes to the reserved private path with `upsert: false`, read back and verify the complete private bytes, then receive `true` from the capture checkpoint. Never remove the source here. |
| `remove_origin` | In a separate claimed pass, read and hash the private copy again, revalidate, remove only the exact pinned public source, then receive `true` from SQL's absence checkpoint. |
| `purge` | With an expired finite deadline, pinned private identity and current purge authority, remove only the exact private key, then receive `true` from its absence checkpoint. Never remove a public source in this stage. |

A duplicate or lost upload response is not proof of capture. Recovery may use the already-existing immutable reserved copy only after its full bytes match and SQL confirms its actual identity. Lost deletion/checkpoint results remain unconfirmed; the same job and exact key recover through the lease/checkpoint mechanism. Transient Storage failures use the retryable `storage_failed` outcome. Actual size/MIME/SHA disagreement uses `source_mismatch` or `private_mismatch` and cannot authorize deletion. The worker does not delete a conflicting evidence copy to make a retry succeed. Deadline/lease exhaustion stops further requests and leaves recovery to the database lease.

`lib/rights-evidence-storage.ts` creates a service client only on invocation. It restricts fetches to the configured HTTPS origin, exact service RPC names and canonical allowed Storage operations. It rejects redirects, signing paths, financial buckets, upsert and multi-prefix deletion. It bounds response time and the complete response body before the SDK allocates a Blob. No source paths, bytes, credentials or raw Storage/DB errors enter worker output; it returns aggregate counts only. No environment file or real key was inspected to implement/test it.

## Case-authorized binary access

`GET /api/admin/rights-evidence/<evidence_id>` takes only an opaque evidence ID. `lib/rights-evidence-access.ts` first calls the authenticated `authorize_rights_image_evidence_read` RPC. No grant means no privileged reader or Storage download. The route then reads and fully verifies the pinned private copy, calls the authenticated grant again, compares immutable pins and returns bytes only if current case/role/policy/risk authority still agrees.

Responses use `private, no-store`, `nosniff`, same-origin resource protection and a fixed image MIME. There is no redirect, signed bearer URL, raw Storage path, provider response header or caller-selected filename. A single bounded HTTP byte range is supported only after full-object hash verification. Invalid/multiple/unsatisfiable ranges do not download a file. HEAD performs no evidence work. Revocation or changed pins after download suppresses the image response. Per-request authorization cannot recall bytes that a previously authorized recipient already downloaded.
