## Confirmed consumer defect and repair

The earlier report tests stopped at submission/record creation. A private salon-reply report stored a parent ID and `/more/reviews?experience=...`; `reportContextPath` correctly removed query/hash, and that customer-history page would run as the viewing moderator. Thus it was not an evidence destination. Public comment/review anchor hints also lost their precise target.

The sanitizer remains unchanged. New `get_admin_social_report_evidence(p_report_id)` accepts only a case ID, requires the existing `admin.reports.read` permission and invokes the existing case-detail access boundary. It resolves canonical text in the database and returns only the reported current body, type, content/parent/salon IDs. It does not impersonate the reporter, expose private parent history/receipts, accept arbitrary content IDs from the admin client, or grant table access.

The resolver validates the stored report source/module and reporter/creator binding. For private-history reply reports, the parent must belong to that report's customer. A forged case pointing at another customer's parent, or an admin-created case pretending to be a customer request, returns unavailable. Public kinds require the actual published/visible parent/salon; private content cannot be exposed by relabeling a forged case as a public target. Deleted/unavailable targets fail closed. This is current live content, not an immutable historical snapshot.

The real admin loader resolves the evidence independently of attachment/conversation loading. Both full report pages and dashboard cases use it. The real `ReportCaseView` shows the canonical text and exact IDs inline, suppresses the misleading customer-account link and does not replace missing evidence with another account's history. Unrelated cases retain their existing context-hint behavior.

The required case-detail response now carries an additive `social_content_report` boolean, derived in the database from that case's source/module under the existing access check. An optional resolver error does not establish case type. Known social cases fail closed; ordinary booking/support/activity cases retain their normal context links, including when conversation and evidence lookups both fail. Loader/render regression checks cover booking and ordinary `/more/reviews` context as well as the known-social failure path. No raw context or additional private history is exposed by the classification flag.

## Notification race defense

Cleanup and insert-time suppression do not guarantee that a concurrent, previously uncommitted notification cannot arrive after a block cleanup. Added a read-time guard to the existing `notification_visible_to_actor` function, preserving its function identity, recipient/staff/booking checks, existing financial suppression and grants. The guard verifies the canonical topic/reply pair and both blocked-author relationships for a Forum notification. It also binds a composite input to a real notification row, preventing the public visibility predicate from becoming an arbitrary private-Forum existence probe.

The existing feed, unread count and mark-all operations reuse this predicate. A new restrictive SELECT policy also covers direct authenticated table reads while retaining the original recipient policy. No ordinary user gains access, no previous financial or booking rule is removed, and unrelated notifications remain unchanged. Physical raced rows may remain internally; they are not returned to blocked recipients on fresh reads. This is stronger than relying on cleanup timing.

`20261109223100_forum_notification_visibility.sql` is idempotent and aborts on an ambiguous/unknown shared predicate shape. `20261109223000_social_report_evidence.sql` adds the case-bound reader. Both are source-only and require current-production/schema/ACL preflight before any separately authorized release. Do not apply the UI ahead of its required database reader.
