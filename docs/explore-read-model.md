# Explore read model and US directory import standard

Implemented October 8, 2026. The database RPC signatures remain compatible with the deployed web and mobile clients. No app deployment is required for this database change.

## Authority and visibility

`locations`, `salon_settings`, `services`, `booking_settings`, `salon_profile_media_assets` and `salon_directory_listings` remain authoritative. `explore_salon_documents` is a rebuildable public-only projection keyed by the existing salon UUID. It does not grant ownership or workspace access. Anonymous/authenticated users cannot read/write the table directly or invoke refresh; the existing public RPCs expose the approved result fields.

Statement triggers refresh the affected old and new salon IDs in the source transaction, including bulk changes and moves between salons. Location rows are locked in UUID order before refresh. Disable discovery, delete settings, deactivate a location, or delete the location: its document disappears atomically. Service/media/booking/category edits update the document. Claim alone does not imply new publication rights. Active owner services take precedence over imported categories. No invented bookable services, prices or review scores are introduced. Time-sensitive `is_new` is computed at read time.

The initial backfill locks source writes for consistency. Normal writes rebuild only affected salons; rebuilds never run on page requests. Multi-salon concurrent maintenance can still deadlock with existing source locks: callers must retry whole transactions on PostgreSQL 40P01/40001; never continue a partial import.

## Read paths

Home recommendations and new salons use indexed document reads with a non-materialized common expression. Unfiltered guest browsing uses an index ordered by profile completeness, update time and salon ID, with a separate lightweight exact count. Filtered search reads the projection instead of joining and aggregating services/media across the directory. Existing state boundaries, result fields, numeric pagination, GPS ranking and recommendation groups remain compatible.

The initial release did not implement preferences or cursor pagination; those are implemented in the subsequent release described below. PostGIS radius expansion and shared response caching remain future work. GPS still allows distant recommendations and omits distance for unknown coordinates. Legacy numbered URLs remain available for compatibility.

## Import contract

Use `scripts/build-wisconsin-salon-import.mjs --state XX --batch-size 500 --batch-index 0`. The legacy filename is retained. The builder recognizes all US states/DC; newly added states require an explicitly verified `--timezone` IANA value. Source file: `data/<lowercase-hyphenated-state-name>-profile-sources.json`. Iterate every batch index shown by the builder; the default now processes **one 500-row batch**, not the whole dataset. Maximum 1,000 records per batch.

Each record needs stable source ID, name, street address, city, 10-digit formatted US phone, nonempty categories, HTTPS provenance URL, collection date, and optional email. An explicit record state must match the selected state. Do not assume an entire state uses one timezone; split and verify mixed-timezone imports. Preserve separate branches at separate addresses. Missing email stays blank. Keep source metadata separate from owner-authored/bookable data.

Mixed-timezone sources can declare a verified `operatingTimezoneIana` on every record. Run the builder separately for each timezone with `--timezone America/New_York --timezone-filter` (and the equivalent for the other zone). Filtering happens before bounded pagination and preserves listing/salon identities. A mismatched record timezone without filtering is rejected. Florida verification uses the city boundary and the Gulf County exception described in 49 CFR 71.5; ZIP alone is insufficient (Mexico Beach and Port St Joe can share a ZIP while using different zones).

Imports serialize the directory ledger and suppression ledger, reject duplicate source IDs, skip existing linked profiles, and avoid exact normalized contact duplicates within the state. Existing claimed profiles and owner settings are never rewritten. Only directory categories for existing unclaimed listings may be enriched. Changes to source ID, phone or address beyond exact identity matching require review; this is not fuzzy entity resolution.

`salon_directory_suppressions` survives profile deletion. It stores a source listing ID and normalized state/city/phone/address identity so a changed source ID cannot automatically resurrect the same contact identity. Hide records are cleared only when the existing profile is explicitly republished. Removal records require privileged explicit restoration. Bulk import must never clear suppressions. A database guard rejects suppressed inserts even if an old importer omits the prefilter. Historical removals made before this ledger existed cannot be reconstructed automatically.

Current builder checks preserve idempotence: repeated imports create zero duplicates. An import is one transaction: all source writes and Explore synchronization succeed together or roll back. Older generated SQL must be regenerated to use batch/suppression rules. All future collectors must feed this contract rather than create independent insert paths. Import identity matching cannot guarantee detection after simultaneous changes to source ID and contact information.

## Reputation request batching

`20261008230001_explore_reputation_batch.sql` adds a bounded public adapter over the existing canonical profile reputation function. The Explore loader requests at most 100 salon IDs per batch and starts reputation loading alongside decision signals, identity and trust evidence, rather than making an additional HTTP request for each card after that phase. For 12 cards, reputation HTTP requests decrease from 12 to one. Larger inputs are split so the 100-ID server limit never silently loses results. Successful batches remain usable if another batch fails.

The original public reputation function still determines visibility and metrics. No shared personalized cache or alternate scoring formula is introduced. A database comparison against the original function reported zero differences for the selected 12 public salons. Adapter tests cover canonical metrics, missing data, 12-card batching, 201-ID batching and exact service prices.

Deployed on the main domain as `dpl_6nZyLTVCxCSytEtVfDWphgVrJR6a`, based on the exact previous production snapshot with only the decision-signal loader changed. Production source was checked unchanged before promotion. Build/TypeScript, ESLint and 13 selected runtime tests passed.

End-to-end measurements from the same local client: before batching, home 7,788 ms and Wisconsin/Nails 3,988 ms. The first post-deploy home request took 11,627 ms; a later request took 5,094 ms. The later Wisconsin/Nails request took 2,781 ms and both later responses contained salon links with no discovery/search warnings. Individual samples include network, rendering and deployment warmup; they establish functionality, not a p95 performance guarantee. The full home still needs further profiling to reach a one-second target.

## Personalization and keyset pagination

Migration `20261008235941_explore_personal_cursor.sql` stores an account's last explicitly selected location and up to five recent service categories. Followed public salons contribute additional category interests, capped to ten distinct categories overall. Preferences are keyed to the current public user; RPC callers cannot select another user. Direct table access is denied and account deletion cascades to preferences. Guests receive general recommendations, explicit filters and their existing browser-saved location; they do not inherit an account's private preferences.

Manual location/filter choices override defaults. A saved account location takes precedence over the workspace suggestion; GPS is used only when requested and precise GPS coordinates are not persisted as preferences. Restoring a guest's browser location now navigates to actual filtered results instead of merely changing the location label. Explicit text/category/location filters restrict eligibility. Interests add a ranking boost when no category is explicitly selected; they never replace that filter. Exact name matches precede less exact matches. For GPS without a text query, measured distance takes precedence over profile completeness. Home recommendations use saved location and category interests; new-salon ordering remains based on creation date. This is transparent deterministic personalization, not an ML model.

New searches and Load more use `search_public_explore_cursor`: score/distance/UUID anchors, no OFFSET. Unfiltered guest browsing has a dedicated composite index. One extra row determines hasMore; the initial exact count is carried forward instead of repeated at every continuation. Each row has its own continuation anchor so a mixed feed can consume part of a batch without skipping unshown salons. The existing organic/personal post sources retain their keyset pagination.

Cursors bind the filters, viewer, frozen interests and a creation cutoff and expire after 30 minutes. Changing filter/GPS/viewer requires a new search; legacy numeric page URLs/cached cursors remain compatible. Newly imported records are deferred until refresh. Removed/hidden records disappear immediately from subsequent requests and deleting an anchor does not invalidate pagination. Source edits can change live ordering; cursor pagination is not a retained database snapshot, so refresh is needed to see all edits/new records consistently. UI deduplication prevents repeated cards. Refresh an expired session rather than treating its failure as exhausted data.

Verification: `tests/explore-personal-cursor.integration.sql` checks five successive pages, uniqueness/state boundaries, changed-filter rejection, expiry, removed anchors, saved account preferences and guest isolation, inside a rollback transaction. Runtime tests additionally verify partially consumed keyset batches reach all 61 fixture salons without repeats. TypeScript and focused lint checks are required before deployment.
