# Four published-data read groups — contract v1

Local source only, 28/10/2026. Owner approved these four groups; no migration, new permission or credentials were applied to production. End-to-end current-revision GoTrue/Owner browser acceptance is pending a separately approved disposable QA run.

## Owner flow

Existing Owner account/current salon → `/market` → **Manage data shared with plugins** → `/market/data`. Four tabs show exact curated fields. Nothing is shared by default; installing an app does not publish data. Owner explicitly edits/selects fields and confirms public sharing/rights before **Publish this revision**. Save draft keeps the live snapshot unchanged; Publish replaces it. Stop sharing is a separate confirmed action and works without revalidating an edited draft. Each write includes expected revision and server-checks the current salon, active Owner and platform gate. Stale writes fail rather than silently overwrite.

These are separate Owner-curated publication snapshots. They do not automatically sync private POS/service/customer tables. Changes to actual salon settings/prices elsewhere do not silently republish a snapshot. Revisit the editor and publish the next revision. The public revision is versioned separately from the workspace edit revision used for optimistic concurrency. A saved draft does not change public data or its revision. The editor loads the draft when present and indicates that plugins still read the live revision. A full restore/history editor is not implemented.

## Scopes / routes / exact projections

All endpoints use server-side `Authorization: Bearer ACCESS_TOKEN`, JSON schemaVersion1, private/no-store/Vary Authorization. No salon/field query overrides. Wrong scope/expired/revoked grant403, no token401, unpublished group404, unavailable infrastructure503. Anonymous database clients still must supply the actual raw scoped token to the public RPC; a stored digest is not a credential.

| Scope | GET route | Data allowlist and bounds |

All groups have a128KiB serialized JSON bound and reject unknown/missing fields. Envelope: schemaVersion, group, salonId, installationId, versionId, synthetic, revision, publishedAt, data. Caller cannot choose another salon; scope/version/tenant comes from the actual installed grant. Manifest allows the four scopes plus the existing optional `salon:identity:read`, with no duplicates. QR sample requests exactly the four groups, not identity or write access. More API scopes are not silently granted to installed versions.

Owner enters list prices in major currency units; conversion to minor units is exact with currency decimal places (USD2, JPY0, KWD3), no rounding extra decimals or currency exchange. Example renders fixed/free/from/on-request correctly. Public price is not a binding checkout quote; null duration is unknown, not zero; no availability calculation.

## Images: originals never reach developers

`GET /api/market-platform/v1/published/media/ASSET_UUID` authenticates/rechecks scope, installation and current selection through a **service-only source resolver**. Direct anon/authenticated calls to that source RPC are denied. Only Reylumi's image gateway uses existing `SUPABASE_SERVICE_ROLE_KEY`; it is not sent to app developers. Missing server configuration fails503. No new service key is generated by this implementation.

Source bytes are fetched only from the configured Supabase origin and fixed salon-profile-media bucket with a validated salon-prefixed WebP path, no redirects,10s timeout,4MiB bound. Raster magic and16M-pixel limits apply; Sharp re-encodes WebP without metadata,≤1920px and≤1MiB output. HTML/SVG/original path are not returned. The metadata-only public API returns no source path. Owner editor may preview their already public profile assets; that is not the developer image API.

Eligibility: active processed salon logo/cover/look/update only, not staff/review photos. Explicit selection and rights confirmation are required. This does not automatically detect a person or verify copyright truthfulness; Owner must not select private/identifiable customer/staff material. Quarantine/deletion/unshare blocks subsequent API requests. Existing public originals elsewhere or downloaded copies cannot be recalled.

## Review / lifecycle / remaining gates

Developer account/org → submit QR manifest version → configure client/sandbox → synthetic API checks → independent exact-hash review → Owner publishes groups and consents/installs → Open/PKCE → server-only grants → responsive menu/QR → data revisions/unshare → version update with new consent → uninstall/revoke. URL/scopes/price/contract changes require new version/review. Owner content revisions do not change the immutable app manifest; externally hosted code drift controls remain a separate design, not certified by these APIs.

No customer PII/raw DB/staff/availability/booking-turn/payment/payroll/write/analytics/AI-provider capability. Owner publication changes only these public snapshots, not booking/POS/refund configuration. Production quotas/distributed abuse controls, public hosting and durable encrypted token/session storage, migration/release integration, actual image-storage and authenticated browser acceptance remain gates. Nothing has been deployed.

## Retry receipts and runtime budgets (local candidate)

Refresh requests may include both `request_id` (UUID) and `retry_key` (`rmk_` plus 32 random bytes in base64url). Reuse exactly that tuple only for the same refresh attempt. The platform stores a client-key-encrypted receipt for 120 seconds and returns the original pair while the resulting grants and current authority still match. The QR reference persists the attempt in its own encrypted state and retries for at most 90 seconds. A different tuple cannot reuse the consumed refresh token. Expired receipts, secret rotation, uninstall, app suspension, account erasure, sandbox reset and a newer rotation deny receipt replay. The legacy refresh request remains single use. No retry key or raw returned token pair is persisted in the platform database.

Authenticated runtime defaults are scoped to each installation/sandbox: 1,200 data reads, 600 media authorizations, 60 code issuances and 60 token issuances per minute. Rate rejection rolls back issuance and returns HTTP 429 with Retry-After: 60 through the Next API. Metadata/media gateway reads both use media authority. These are local resource guards, not a claim of production capacity. Edge-level unauthenticated flood controls, retention/alerting configuration and real hosting load acceptance remain provider gates. Rejected token/authorize requests emit a request reference and sanitized reason only; bodies, query strings, cookies and credentials must stay excluded from proxy/provider logs.

New migration files remain unreleased draft source in this local iteration. Earlier draft revisions ran only in disposable named fixtures that were closed. No shared/cloud/production database has applied them. Freeze their final hashes before any shared QA application; later changes must use additive migrations.
