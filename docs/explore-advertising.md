# Explore advertising

Admin → Advertising manages popups, sidebar/mobile-feed image campaigns, and scrolling announcements. Requires `admin.businesses.update`. Images accept HTTPS URLs or uploads of JPG, PNG, WebP and GIF up to 10 MB. Choose Saved draft to prepare a campaign without running it. Dates in the editor are UTC; popup “again tomorrow” resets at midnight America/Chicago.

The manager has Running, Saved, Stopped and Create new tabs, with Edit / Run / Stop / Delete actions on each row. Status is stored in campaign configuration; existing enabled campaigns appear under Running and existing disabled campaigns under Saved. Creating a campaign opens a fresh editor with its own identity; repeated save attempts keep that editor's identity. Validation errors appear beside the relevant inputs and retain all entered values. Images and destinations are optional: a campaign without an image displays its name/message; a campaign without a destination is informational and does not navigate. Announcements without text use the campaign name.

Apply `supabase/migrations/202610060002_explore_advertising.sql` and `202610060003_explore_reference_favorites.sql`. Server requests use the service role; tables have RLS and are inaccessible to anonymous/authenticated database clients. Set `ADVERTISING_IP_HASH_SECRET` to a stable random secret on all instances. The service role key is the fallback; rotating that fallback resets frequency history. Raw IP addresses are never saved. Vercel automatically uses `x-vercel-forwarded-for`. Otherwise set `ADVERTISING_TRUSTED_IP_HEADER` to the header overwritten by the hosting proxy (`cf-connecting-ip` for Cloudflare; default `x-forwarded-for`). Direct local hosting without an IP header uses a secure HTTP-only visitor cookie. Shared IPs share popup limits.

A visit selects one active campaign per format. Placement rotation excludes the previously shown item when alternatives exist. Mobile ads appear after every four feed cards, or once in shorter feeds, and between search results. Popups claim an impression atomically when their delay expires. Disabled campaigns and schedules are checked again at claim time. A popup cannot have both no close button and no auto-close duration. GIF animations are served unchanged.

Guest Love/Book actions invite signup/login. Same-tab pending actions expire after 24 hours; on returning to Explore after authentication, saved posts and salon favorites are saved, booking opens, or a contact notice appears. Directory entries and inspiration previews have a separate favorites list at `/explore/favorites`; actual posts and followed salons keep using the existing account libraries. Server booking settings remain authoritative; no booking feature is enabled by these UI changes.

Validation: `node --test tests/explore-advertising.test.mjs`; run `tests/explore-advertising.integration.sql` against the linked database (its fixture rolls back). Browser coverage: `tests/explore-advertising-runtime.test.mjs` uses `ESBUILD_MODULE_PATH` and `TEST_BROWSER_PATH`.

Campaign targeting supports multiple workspace audiences (Guest, Personal, Staff, Owner), devices (Desktop, Mobile), and page prefixes. Select more than one prefix or add custom paths; `/` includes all application pages except Admin. Placement formats support sidebar, Explore mobile feed, page start and page end; page positions render inside the navigation content. Audience targeting follows the selected workspace and is filtered again by the API. Existing campaigns retain Explore / all audiences / both devices defaults.

Explore feed slots use one shuffled campaign queue per page visit. Each slot takes a different campaign; remaining slots are empty when that queue ends. Returning to a page starts a new visit. Placement duration begins when the ad reaches the viewport, so ads lower in a feed do not expire before being seen. Mobile announcements appear immediately at the top; popup timing waits at least eight seconds after an announcement. Popups support arrival delay or a configured scroll-progress threshold. Both remain subject to the configured IP frequency policy. These features apply to the shared responsive web/PWA UI; a separate native mobile client is not verified here.


Reports & limits (202610070005_advertising_insights.sql)

The Reports & limits tab reports unique campaign views and clicks per browser session, new-account conversions, CTR and signup/click rate. Filter by 7/30/90 days, desktop/mobile and workspace audience. Events are attributed back to the original impression date in America/Chicago, preserving consistent rate cohorts when signups happen later. Snapshot names and formats retain report history after a campaign is deleted. Tracking starts with this release; historical activity cannot be backfilled reliably.

A view is admitted when a placement reaches the viewport or a popup/announcement is presented. The database atomically enforces the session cap and popup frequency policy; a failed admission is not an impression. Default limits: six unique campaigns, one popup, 60 seconds between popups, 30-minute inactivity expiry. Sessions use an HTTP-only browser cookie shared across tabs. Page and ad requests refresh the expiry. Limits can be changed by administrators; zero disables delivery. Events never store raw IPs or private page tokens; paths are reduced to their first route segment.

Conversion attribution uses the last accepted advertising click within seven days, signed in an HTTP-only cookie. Email signup, auth callbacks for newly created accounts and staff-invite signup record conversions server-side. Existing users and obfuscated duplicate-signup responses are excluded; each new auth user is counted once. Signup creation success is counted before any required email confirmation; this is not an activated-account metric. Tracking failures never prevent signup. Preview displays saved campaigns or an unsaved draft (including a selected local GIF) without navigation, impressions, clicks or budget usage. Choose device, audience, page and placement inside the preview.


Owner campaigns (202610080002_owner_campaigns.sql)

Owners have `/campaigns` under More, with My campaigns, Results and Payment. Post menus offer Get more people only in the current salon's owner workspace. Successful publication queues the exact post; the shared owner layout claims at most one suggestion per configured cooldown across tabs. Suggestions expire after 24 hours, do not interrupt an existing modal, and never show in portable POS or Admin. Only an owner's own publication produces an automatic suggestion; salon posts can also be promoted manually by an owner. Beauty posts require the owner's authorship, a public Beauty profile and salon attribution. Hidden, deleted, unpublished, held posts and inactive salons cannot be advertised.

Setup offers city, neighborhood, ZIP/postal code, state/region and country, editable daily view limits and 1–90 days subject to admin limits. Smaller areas require state/country, and neighborhoods require city. Suggestions and example engagement ratios are admin configurable. The prominent example numbers are explicitly illustrations, separate from real reporting. The server recalculates price in integer USD cents; it locks salon creation, limits open campaigns and allows one open campaign per post. Repeated save requests use the same campaign ID.

Payment is deliberately unavailable until provider setup. Save creates `awaiting_payment`; no card form, browser card storage or simulated paid state exists. Future provider integration must use hosted secure card collection, store provider customer/payment-method IDs only, verify webhook signatures and currency, and call the service-only payment-confirmation function with the agreed total authorized budget and a unique provider reference. Admin approval starts the configured duration. A stored card must still pass provider authorization before approval. The accounting model spends only on admitted views; the future provider must capture actual spend and release/refund unused authorization after cancellation, rejection or completion. These provider calls are not implemented in this release.

Sponsored posts occupy one Explore feed slot on desktop and mobile. Location comes from the visitor's explicit Explore selection, resolved to an unambiguous known location. City/state/country input and ZIP codes are supported. Neighborhood selection uses `Neighborhood, City, State, Country`. Unknown, missing or ambiguous places get no owner ads rather than broader targeting. No background location collection occurs. The viewer can hide the card. At least 50% visibility for one second in a foreground tab precedes admission. Campaign tickets expire after ten minutes, bind visitor, signed-in user and exact area, and cannot be altered or replayed to add views. The request endpoint accepts view and click only; client requests cannot claim likes, comments or bookings.

Delivery considers one post per salon before ordering by delivered proportion of the booked view limit, with visitor-specific tie breaking. This prevents one salon's multiple posts occupying the entire candidate list. Per-campaign database locks enforce time, post eligibility, payment, approval, budgets, view caps, frequency and evenly paced daily delivery. A visitor lock enforces the global owner-ad cap across concurrent campaigns. Defaults are two views per campaign per day and six owner-ad views in total per day; Admin can change both. Logged-in visitors share frequency across browsers; guests use a configured trusted proxy network hash, or a browser cookie when no trusted header is configured. No raw IP is persisted. Existing platform advertising retains its own settings and counters.

Pause and cancellation stop new admitted views immediately. Pause keeps the original end date. Budget exhaustion or expiry stops delivery; opening the owner page completes expired campaigns. A post becoming unavailable or the original advertiser losing owner access pauses delivery. Another current salon owner may cancel old campaigns, but payment ownership is not silently transferred.

Real engagement is attributed to the last authenticated sponsored-post click for the same post within seven days. Database triggers record successful Love/save actions, visible non-salon comments, approved legacy booking requests and confirmed public bookings. Each person contributes at most one result of each kind per campaign; repeated edits, retries or later booking status transitions do not inflate results. Likes here include the existing Love/save action. Anonymous clicks do not produce attributed engagements until future login attribution is connected. Organic totals remain separate. Counters describe actions achieved, not the current number remaining after unsaving, deleting a comment or cancelling a booking.

Apply the owner campaign migration after the existing baseline, post safety and booking migrations. This work does not apply migrations or deploy to production. Verification: owner-campaign-rules.test.mjs, owner-campaigns.integration.test.mjs and owner-campaigns-runtime.test.mjs. Browser fixtures verify desktop/mobile setup, input retention, saving, dismissal and focus restoration; visual captures are under artifacts/owner-campaigns. Provider/card handling and a live paid production campaign are intentionally unverified until payment setup.


## Campaigns Market feature and credits (2026-10-08)

Campaigns is a free, salon-scoped Market feature. Owners must add it before seeing the workspace, promote action or post suggestion. Removing it pauses running ads, disables automatic purchases, hides entry points and keeps credits, ads and results. Reinstalling gives no extra welcome credits. The welcome grant ledger persists independently of account deletion and is unique by salon, owner and normalized-email hash. This prevents repeated install/remove rewards; it is not a guarantee against creating unrelated identities.

Defaults: 100 credits = USD 1; gift 300 credits; 500 daily views for 3 days in a city costs 300 credits. ZIP/neighborhood costs 80%, city 100%, state 150%, country 200% of base price. Daily base credits = max(admin daily minimum, ceiling(daily views × 100 / admin views per dollar)). Round scope price up to an integer each day, then multiply by duration. Admin can change gifts and scope percentages; existing campaign prices and grants stay fixed. Views and engagement estimates are not guaranteed results.

Owners can upload one JPG/PNG/WebP under 5 MB with a headline/message. Images are decoded, resized and re-encoded without metadata, stored privately, and served with short-lived signed links. Standalone ads require the same credit reservation and admin review as promoted posts. Admin can preview the actual photo and message before approving. Public standalone ad pages link to the salon and booking. Confirmed bookings without another source can be attributed to the latest signed-in custom-ad click at the same salon within 7 days. Custom ads have no independent like/comment controls.

Available credits move to reserved credits before review. Real admitted views consume the agreed price proportionally, rounding cumulative charges up to integer credits. Pausing holds the remainder and preserves the original end date. Cancellation, rejection or expiry returns unspent credits. Reservation, consumption, refund, gift and renewal use serialized wallet/campaign updates. Replay tickets and payment receipts are idempotent. Original direct cash confirmation is disabled for this feature.

Keep running is a separate opt-in per campaign. Each expired period returns unused credits and reserves another agreed period if funds are sufficient. Otherwise the ad finishes; it may renew after funds arrive if keep running is still selected. Removing the feature clears this choice. Automatic credit purchases are off by default and separately require a securely saved card, explicit permission, selected pack, low-balance threshold and monthly automatic-purchase cap. Ongoing ads can also request funds for their next period. Card failures disable automatic purchases; uncertain outcomes retain the same order/idempotency key. A payment already initiated may finish after the user turns the setting off. Credit purchases are 500/$5, 1,500/$15 and 5,000/$50. Unused credits return to the wallet, not the bank card.

### Activation prerequisites

Apply migrations 202610080002, 202610080003 and 202610080004 in order. Production migrations 002 and 004 were applied on 2026-10-08; 003 was already installed. Migration 004 creates the private campaign-creatives bucket. The service-role server client must be configured.

For purchases, configure server-only CAMPAIGN_STRIPE_SECRET_KEY and CAMPAIGN_STRIPE_WEBHOOK_SECRET. Configure Stripe to send payment_intent.succeeded and checkout.session.expired to /api/campaigns/payment-webhook. Set the trusted metadata base URL for checkout returns. Missing credentials leave credit purchases and automatic top-ups unavailable; welcome credits still work.

The authenticated /api/internal/campaign-credits handler runs top-ups and renewals. Production uses Supabase pg_cron and pg_net every 15 minutes, configured by migration 202610080005, because the current Vercel Hobby plan only allows daily Vercel jobs. A dedicated CAMPAIGN_QUEUE_SECRET is stored in the production environment and encrypted Supabase Vault (campaign-credit-queue). The worker also accepts CRON_SECRET as a fallback. Renewal is processed on the next worker run, not guaranteed at the exact second of expiry. Do not enable keep-running in production without an operating worker. Payment credentials are environment-only in this version; the future admin payment-provider setup remains to be connected. No real card charge has been performed; the deployed payment UI remains unavailable until Stripe credentials are configured.

Validation includes SQL integration tests for installation, gift persistence and identity reuse, credit pricing/reservation/refunds, custom creative eligibility, renewal and payment replay; signature/fulfillment tests; and mobile/desktop popup, custom-ad and Credits-page browser checks.

Production validation runs installation, gift deduplication, custom creative creation, reservation, approval and cancellation/refund in one rollback transaction against an existing active owner workspace. No test ad, wallet or welcome grant is retained. The scheduler endpoint is also tested with a Vault-authenticated pg_net request after deployment.
