# iOS moderation operations — 2026-11-18

This is a local source audit and tested implementation candidate, based on `04128e40de1a2ce22170c0fc95ea053668c29e26` plus the scoped patch below. It is not evidence that the hosted database, production UI, staffing, provider or App Store submission has changed. No real user data, real moderation decision, provider request, commit, push or deployment was used. Other concurrent task changes are outside this patch.

## Implemented boundary

`supabase/migrations/20261118210000_moderation_operations.sql` replaces exactly three existing helpers, with their signatures and client grants retained:

- `beauty_public_post_exists`: public visibility now also requires `safety_hold=false`. A missing/private Beauty profile, deleted post or nonvisible moderation state remains unavailable.
- `post_comment_target_is_public`: Salon looks and updates also require no safety hold; Beauty uses the hardened existence predicate. Existing salon publication and bidirectional personal-block conditions remain. This predicate feeds direct comment SELECT/INSERT RLS, public comments RPC and counts, so a held parent cannot leak comment bodies/counts merely because other publication flags remain public.
- `post_user_block`: resolve a post's author only for an active signed-in viewer and a currently eligible public post. Previously, any known private post UUID could be blocked and its author then learned through `get_my_blocked_users`. A successful public block can be retried by the same blocker while the underlying post is still public. It cannot turn a reverse-only block into an author probe or use a held/private/deleted target. Responses contain capability/blocked booleans only. The existing `set_user_block` mechanism remains responsible for the pair and its social side effects.

All three are SECURITY DEFINER with explicit `pg_catalog, public` search paths and explicit anon/authenticated grants. No financial records, salon memberships/roles, report decisions, existing holds or content are migrated. No new automatic restriction/preapproval is introduced.

The tests execute the previous actual SQL definitions to reproduce both defects, then apply the actual migration. They are not mocks of the predicates being fixed. The bounded PGlite fixture is not a full schema; the separate isolated Supabase run below exercises the full current migration set and real Auth/PostgREST/RLS.

### Appeal and false positives

`20261008233001_review_case_communication.sql:375` allows an authorized reviewer to reopen a resolved **user-origin** post report only after reporter reconsideration/new-evidence workflow state. It retains decision history and does not restore content. The current Support conversation belongs to the reporter; it is not automatically an author appeal inbox. An author or guest can use Contact Support for a false-positive complaint. A dedicated author appeal/recovery workflow and operational response ownership still need acceptance; do not describe them as complete merely because a report receipt exists.

Keyword matches and duplicate/device/volume signals remain monitoring signals under `20261029021000_social_monitor_only.sql:202`. Existing manual holds and access restrictions stay enforced. This patch does not reinterpret monitoring as image approval or add routine admin approval.

### Raw media and takedown

Existing admin Delete (`202610070007_post_safety.sql:156`) changes the post/row and case state, not Storage bytes. The canonical post action does the same (`20261017194500_post_actions_canonical_caption.sql:41`). Neither body performs Storage removal. Beauty post media rows/public objects can remain; Salon assets may be referenced elsewhere. A separately copied cover is a separate asset.

The `beauty-profile-media` and `salon-profile-media` buckets remain public; `20261116220000_public_image_safety.sql:5` creates a **private staging bucket**, not a private public-output bucket. Protected final paths are immutable to clients. The public-image server helper currently uploads final copies with `cacheControl: "31536000"` (`lib/public-image-safety.ts:91`). Hiding/deleting an app row therefore does not by itself revoke a known public object URL or recall browser/CDN/downloaded/third-party copies. No Storage purger or cache invalidation was added here. This is a material operational limit to review before asserting effective media takedown; no live CDN behavior was measured in this task. Preserve shared asset references and private bank/payroll/tax retention boundaries when designing a remedy.

## Exact-text operation proposal — pending approval

Artifact-only preview: `artifacts/ios-moderation-operations-20261118/exact-text-controls-preview.html` plus desktop/mobile PNGs. It reuses current report-panel CSS and synthetic evidence; buttons are nonfunctional. Root reviewed the artifact; user approval and product wiring are pending. No additional Remove/Restore backend or product UI has been added.

Keep **Record resolution** as the existing Support lifecycle action (`app/(app)/admin/reports/report-case-view.tsx:51`). A separate content section would use **Remove from public view** / **Restore prior visibility**, with reports.update, a required reason, canonical case-target binding, row locking, current evidence version, idempotency and immutable decision audit. Restore must never resurrect author deletion/withdrawal/private content or bypass another hold. An appeal or a generic case resolution must not auto-restore.

Target semantics: comments have `published/visible/hidden/deleted/reported`; reviews have `visible/hidden/reported/withdrawn`; review replies have `visible/hidden/withdrawn`. Existing comment `reported` state is guarded against author release by `abuse_guard_content`. Experiences and experience replies have no dedicated public-moderation state; `feedback_state`, `issue_status`, sentiment, reputation/Truth evidence and POS identity are business facts and must not be repurposed. A followup needs a separate moderation state/ledger plus complete public read/aggregate filtering and appeal eligibility tests; preserving records is preferable to deleting canonical visit/financial evidence. A new backend operation alone would not establish a user-usable reviewer flow until a control is wired and accepted.
